Early release package: Orbit · Vista · Aster

Modernize your backend one capability at a time.Preserve existing value. Create room for change.

NOVA aims to expand services on your existing backend, then transition individual capabilities when ready. Vista serves users, Orbit coordinates requests and is designed to work with many different existing systems, and Aster is an independent demonstration backend that does not use a running system; its implementation is being planned. Nexus, the build and operations toolkit, joins in a later phase.

Model overview

A clear path from the user to the backend.

Orbit adapts how application requests are received and is designed to work with many different existing systems. Vista provides the workspace for incremental modernization (Strangler Fig). Aster is an independent demonstration backend that does not use a running system. Nexus build and operations tools belong to a later phase.

Request flow

Four steps of a request.

How a request moves through the model.

01

Users act in Vista

Choose a function, fill in forms or work with tables; the browser only interacts with the workspace.

02

The Gateway forwards securely

The server-side connection layer receives actions from Vista and forwards requests to Orbit under the agreed security configuration.

03

Orbit verifies and runs the flow

Validate the token, accept the request into a bounded queue and run the matching business flow.

04

The existing backend handles the work

Orbit passes the request to the existing backend (or to Aster in demos), receives and checks the result, then returns a screen or data to Vista.

Components

One responsibility per component

The early-release package has three components, each with its own role and able to change independently.

01

Vista — one unified workspace

Menus, tabs, tables and forms in one working interface, so users can move between business functions without relearning how to work.

02

Secure sign-in sessions

The design keeps connection credentials on the server, separate from the user interface. Authentication and session requirements are agreed during integration.

03

Orbit — customizable connection gateways

Customizable ingress gateways adapt to existing application calls and data formats. They share business orchestration, with the aim of limiting changes to connected systems.

04

Coordinated business flows

Flows coordinate business steps with time limits, cancellation and load control. Each change is tested against its backend and intended scope of use.

05

Aster — independent demo backend

An independent demonstration backend that lets the working flow be shown without using a running system. Aster is being planned for implementation.

06

Demonstrations apart from live systems

Lets the flow from Vista through Orbit be shown without touching a running system. Evaluation on a real backend still needs compatibility review and an agreed test scope.

Deployment questions

What needs to be clear before deployment.

Do we need to replace the entire backend at the outset?

You can begin by letting Orbit work with existing programs and data after checking compatibility. The direction is to expand services, then transition individual capabilities when ready; each change needs its own scope and testing.

Does Vista replace the current interface immediately?

Not necessarily. Start with one group of functions and run it alongside the current interface.

How is Orbit different from a typical API gateway?

Orbit combines customizable connection gateways with shared business orchestration, session management, timeouts and load control. A suitable gateway can preserve existing client calls and data formats; compatibility is verified before adoption.

What is Aster?

Orbit is designed to work with many different existing systems. A live system cannot always be used for demonstrations, so Aster was created as an independent demonstration backend. Aster is a separate item within NOVA and its implementation is being planned; having Orbit work with a real backend needs compatibility review and an agreed test scope before deployment.

Does the demo run on my real system?

The demo is intended to use a demonstration backend (Aster) to illustrate processing separately from your running system. Evaluation on a real backend requires compatibility review, a connection profile and an agreed test scope.

What happens when a transaction outcome is unclear?

The system stops and reports clearly; it does not replay the transaction automatically. Operations reconcile through the agreed process. A timeout does not mean the transaction was rolled back.

What is needed to deploy?

A compatible business backend, servers for Orbit and the Gateway inside the internal network, and acceptance criteria. Versions, security and capacity are agreed per deployment; Orbit is not exposed directly to the internet.

Where does Nexus fit in the model?

Nexus is a later-phase component. Its build, environment and test-data tools have been used in real environments on their own, and the integrated NOVA experience belongs to a later phase. Evaluating the early-release package does not depend on it.

Where does Echelon fit in the model?

Echelon is a peer component in a later phase. Vista connects to Orbit; Echelon adds orchestration when a flow needs task sharing across multiple agents, load balancing or per-step error handling.
